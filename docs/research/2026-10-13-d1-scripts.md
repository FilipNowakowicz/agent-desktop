# D1: the agent writes scripts instead of single steps (negative result)

Date: 2026-10-13. The cheapest test of direction D1 on the
[directions board](../project/DIRECTIONS.md): one tool that runs Python in the
session with a small library, compared with the current tools. Gate from the
board: **turns −50% or more on the table task at equal success**. Measured on
this machine with Claude Code 2.1.296 through `claude -p`, Opus 5.5.

**Result: the gate was not met.** Pooled over three tasks, turns fell 4% (not
significant) and wall time rose 58% (p 0.001). Scripts cut looks 27% and input
tokens 17%, and on the two multi-record tasks turns fell about 20–25%, but each
turn took longer: writing a script costs model time, and scripts spent more
time in the tool. On the single-record admin task every measure was worse.

## Treatment

`desktop_run` (`AGENT_DESKTOP_RUN=1`, experimental, off by default) runs a
Python script in a subprocess as the server's controller. The script starts
with `from agent_desktop.script import *`:

- `find(element, role, text, state, exact, window, app, within)` over the
  accessibility listing, `one(...)`, `text(...)`, `rows()` (table rows as cell
  texts); `within="mallory"` keeps the innermost row, list item, dialog or
  form containing that text; among nested matches the innermost wins (Chromium
  names a cell after its button);
- `press`, `set_text`, `select`, `act(node, action)`, `type_text`, `key`,
  `click`, `scroll`, `focus`, `windows`;
- `wait(...)` as `desktop_wait`, raising `TimeoutError`; `home()`;
  `browser(...)`; `screenshot()`.

Any exception stops the script and is returned with stdout and stderr. It is
refused on host sessions.

Arms: **pixels**, the current tools (`--tools full`); **code**, `--run --tools
code`: only `desktop_screenshot`, `desktop_ui`, `desktop_windows`,
`desktop_wait` and `desktop_run`, so scripts are the only way to act. The
first pilot offered `desktop_run` beside every other tool; the agent never
called it (as with S2 guards and E2 expectations), so the test needs the
code-only arm.

`within`, `rows()` and the innermost-match rule were added after two pilot
runs (seed 1) showed the agent chunking the flat cell list by hand and
indexing Edit buttons by position. The A/B used seeds 2–4 and one task
(`real-expense-claim`) that no pilot had seen.

## Runs

Three seeds × three tasks × two arms = 18 runs, all passed:
`artifacts/benchmark/20261013-004337-7604` to `20261013-010248-b817`. The arms
were not interleaved for every task: a shell quoting error (zsh does not split
an unquoted variable) made the first code-arm runs fail at argument parsing,
so the code arm of the two Chromium-only tasks ran afterwards, and
`real-expense-claim` (Mousepad from `nix shell nixpkgs#xfce.mousepad`) ran as
interleaved pairs at the end. Pilots (`20261013-003510-e9f5`,
`-003608-0a64`, `-003802-d7d7`, `-003923-cdd6`) are not counted. Aggregates:
[`benchmarks/results/2026-10-13-d1-scripts.json`](../../benchmarks/results/2026-10-13-d1-scripts.json).

Time split (pilots and A/B): model time was not lower with scripts (inventory
42–64 s against 42–57 s; admin 30–59 s against 20–34 s), and tool time was
2–4 times higher (12–56 s against 4–18 s): every lookup lists up to 2000
accessibility nodes, and agents put `time.sleep` after actions.

## What the transcripts show

- **The agent still works one step at a time on an unfamiliar UI.** Most
  scripts do one or two actions and then print part of the tree to see what
  happened. The board named this risk: the agent has to look before it can
  write the program.
- **Loops do appear when the task repeats.** On the inventory task the agent
  wrote a loop over pages and matching rows (one 15 s script edited several
  rows). That is where turns fell, but not by half.
- **Accessibility gaps push it back to pixels.** Unnamed fields, rows Chromium
  only exposes when on screen, and a combo box without a set-value action led
  to `click(x, y)` inside scripts.

## Decision

D1 in this form stops: scripts do not reduce turns enough on unfamiliar tasks,
and they make tasks slower. The tool and library stay experimental and off by
default. What would change the picture:

- reuse: a script that worked is a candidate skill (E6) for a repeat of the
  same task, where no exploration is needed;
- tasks with many more records than these (tens of rows), where one loop
  replaces many turns;
- cheaper lookups (one listing reused across a script, no full listing per
  call), which would cut tool time but not model time.

None of these is planned; they are recorded on the directions board.
