# E6: verified skills for repeated tasks (negative result)

Date: 2026-10-13/14. E6 on the [project plan](../project/PROJECT_PLAN.md),
reopened after [D1](2026-10-13-d1-scripts.md) named reuse as what could change
its result: an agent that solved a task writes a script for the whole task; the
harness checks it on new data; a later agent gets it. Gate: **repeat runs at
least 3× faster in wall time at equal success**. Measured on this machine with
Claude Code through `claude -p`, Opus 5.5, `--run` (`desktop_run` beside the
usual tools) in every arm.

**Result: the gate was not met** (a follow-up below, giving the skill by path,
reached 2.8–2.9× on two tasks). With the skill, all 9 repeat runs passed (as
did all 9 baseline runs), turns fell 62–77% and cost 23–61%, but wall time fell
only 1.3× on the two short tasks and doubled on the inventory task. Replaying a
skill without any model was 4.6× and 12× faster on the two short tasks but
failed every time on the inventory task, and that skill's own asserts reported
success while the task's check failed.

## Treatment

`scripts/benchmark.py` gained three options:

- `--learn DIR`: the prompt asks the agent to end its final reply with one
  script for the whole task (between `SKILL-START` and `SKILL-END`) that finds
  its data on the screen, uses no values from this run and ends with asserts.
  The harness reads the full final reply from the transcript and saves
  `DIR/<task>.py`.
- `--replay DIR`: no agent; the harness runs `DIR/<task>.py` through
  `desktop_run` on a fresh task and then runs the task's own check. This is the
  verification step and the no-model ceiling.
- `--skill DIR`: the agent gets the script in its prompt and is told to run it
  (adapted if needed), confirm the result, and finish the task itself if it
  fails.

Tasks: `real-expense-claim` (files plus Mousepad plus a browser form),
`real-ticket-config` (a config file from a ticket) and
`real-inventory-cleanup` (a paginated browser table, an edit dialog per row and
an interrupting dialog). Seeds change rows, names, numbers and paths.

## Runs

All in [`benchmarks/results/2026-10-14-e6-skills.json`](../../benchmarks/results/2026-10-14-e6-skills.json)
with the skills' source:

1. **Learn**, seed 1: 3/3 passed (expense 76.8 s, ticket 39.3 s, inventory
   148.7 s) and 3/3 returned a skill (`20261013-020924-397e`).
2. **Replay**, seeds 5–7: expense 3/3 (10.2–10.6 s), ticket 3/3 (1.9–2.0 s),
   inventory 0/1 (`AssertionError: no Norvik products found`).
3. **Inventory repair**, seed 5, skill given plus `--learn`: passed in 282.8 s
   and returned a new skill (`20261013-233135-1ca4`). The first attempt
   (`-021502-ef2e`) hit the account usage limit and is excluded.
4. **Repaired replay**, seeds 6–7: 0/2. The script exited 0 and printed
   `OK 2 products marked Discontinued` (and 3), but it had read 52 of 60 rows,
   so the task's check failed.
5. **Gate**, seeds 6–8 × 3 tasks: baseline (`--run`) then skill (`--run
   --skill`, expense and ticket from step 1, inventory from step 3). Not
   interleaved: all baseline runs came first, the skill runs about 10–25 min
   later. A first skill batch failed at argument parsing (an unquoted zsh
   variable, as in D1) and is not counted.

## What the runs show

- **Model time has a floor that a skill does not remove.** The agent still
  reads the prompt, writes the script back out as the `desktop_run` argument
  (output tokens barely fell: the skills are 2.6–4.2 kB) and confirms the
  result. That leaves 13–22 s of model time on tasks a replay finishes in
  2–10 s.
- **A script written once is slow to run.** The inventory skill reads every
  page twice, sleeps after each step and lists the whole accessibility tree
  for every lookup: 116–230 s of tool time against 17 s for the agent.
- **Skills depend on state the agent did not see.** The learned inventory skill
  scrolled with the pointer wherever it was; in the learning run an earlier
  click had left it over the page, in a fresh session the wheel did not reach
  the page, `find` saw no page label, and the script treated the table as one
  page. Chromium exposing only rows on screen made the repaired script miss
  rows too.
- **A skill's own asserts are not verification.** The repaired skill checked
  the rows it had read, not the table. Only the harness check, which knows the
  answer, caught it. A skill registry needs an independent check per task, which
  ordinary tasks do not have.
- **The agent made up for a weak skill.** The repaired inventory skill failed
  both of its replays, yet all three inventory skill runs passed: the agent ran
  it (2–4 `desktop_run` calls), checked the result and finished the task in 4–7
  turns.

## Decision

E6 in this form stops: it saves turns and money on repeats but not the wall
time the gate asks for, and an unchecked skill can report success on a wrong
result. The `--learn`, `--replay` and `--skill` harness options stay for later
experiments; nothing changes in the product. What would change the picture:

- running a stored skill by name (no re-emitted script), with the agent only
  choosing arguments and reading the result: model time would approach one
  short turn;
- skills checked against the effect, not their own reading (a file, a config
  key, a server response), which suits file and config tasks more than paged
  web tables;
- cheaper lookups in `desktop_run` (D1 found the same tool-time cost).

## Follow-up: the skill by path

The first lever above, tested the same night with no product change.
`--skill-path` (with `--skill`) gives the agent the skill's file path instead
of its code, with the exact call `exec(open(PATH).read())` for `desktop_run`,
and says that exit 0 means the task is done. Pilot: ticket, seed 9, passed in
8.4 s (`20261014-000935-53b9`, not counted). Arm: seeds 6–8 × 3 tasks
(`20261014-000958-ca67`, `-001500-5a90`, `-001706-c36b`), all 9 passed,
compared with the baseline above (run about 25 minutes earlier, not
interleaved).

| Task | Arm | Turns | Wall time | Model time | Tool time | Input tokens | Output tokens | Cost |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| real-expense-claim | base | 16 | 47.3 s | 39.2 s | 6.4 s | 374k | 2.9k | $0.32 |
| real-expense-claim | path | 2 | 16.2 s | 3.6 s | 10.5 s | 29k | 170 | $0.04 |
| real-ticket-config | base | 8 | 22.4 s | 15.5 s | 4.9 s | 104k | 1.1k | $0.13 |
| real-ticket-config | path | 2 | 8.0 s | 4.0 s | 2.0 s | 29k | 219 | $0.04 |
| real-inventory-cleanup | base | 22 | 72.7 s | 53.7 s | 17.1 s | 665k | 4.0k | $0.49 |
| real-inventory-cleanup | path | 9 | 156.2 s | 24.2 s | 137.0 s | 158k | 2.0k | $0.19 |

Speed-up against the baseline median: **expense 2.92×, ticket 2.80×**,
inventory 0.47×. The gate (3×) is narrowly not met; cost fell 66–87% on the
two short tasks.

- **The agent's share is now about 6 s:** 2 s of `claude` start-up and
  3.6–4 s of model time over two turns. The rest is the script's own run time.
  A dedicated "run skill by name" tool would not shorten this further: the
  call is already one line.
- **What is left is the script's speed.** The expense skill spends about 4 s
  of its 10 s in fixed `time.sleep` calls. Removing them would probably clear
  3×, but that is tuning after the measurement and is not claimed here.
- **Inventory: every first call hit `desktop_run`'s 60 s default timeout.**
  The agent then ran it again with a longer timeout or finished by hand, and
  checked even when the script said OK (seed 6: `OK 3 products`, 52 rows read).
  All three passed, but slowly.
- **Benchmark leak:** in one inventory run the agent printed the page source,
  which contains the task's row data and judge code. Whether it used them was
  not checked; the realistic web tasks should keep the checker out of the
  page.

E6 stays stopped: replaying a verified skill is the right shape for a repeated
task, but the gate is met only when the skill itself is fast and its check is
independent, and neither comes from the agent's first script.
