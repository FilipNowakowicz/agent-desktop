# Possible Future Direction: Portable NixOS Agent Environment

This is an extension to the previous project vision. **Do not change the current Linux MVP or begin implementing this yet.** Record this as a potential architectural/product direction and keep it in mind when making decisions that would unnecessarily prevent it later.

## Core Idea

The project currently starts as a Linux-native agent runtime/private desktop.

A potentially much larger direction is to make the **Linux/NixOS environment itself the portable execution platform**, even when the user's host operating system is Windows or eventually macOS.

Instead of independently implementing the entire runtime for:

- Linux
- Windows
- macOS

we could potentially standardize the environment in which the coding agent actually operates.

Conceptually:

```text
                    Agent Runtime
                         │
          ┌──────────────┼──────────────┐
          │              │              │
        Linux          Windows         macOS
          │              │              │
        native       managed Linux   managed Linux
                         │              │
                         └──────┬───────┘
                                │
                              NixOS
                                │
                     identical agent runtime
```

Linux would run the runtime natively.

Windows could run a managed NixOS/Linux environment behind a native application.

macOS could potentially use a similar architecture later.

The important idea is:

> Linux could become the project's portable agent execution platform rather than limiting the product to Linux users.

## Windows User Experience

The user should NOT feel like they are manually operating VirtualBox or managing a VM.

The experience should be closer to Docker Desktop.

For example:

```text
Install Agent Runtime
        ↓
Select/open repository
        ↓
Give coding agent a task
        ↓

┌─────────────────────────────────────────┐
│ Agent Runtime                    Running│
│                                         │
│ Task: Fix settings crash               │
│                                         │
│ Build        ✓                          │
│ Tests        ✓                          │
│ Application Testing...                  │
│                                         │
│ [View Desktop] [Inspect] [Pause]        │
└─────────────────────────────────────────┘
```

Internally:

```text
Windows
│
├── Native Agent Runtime UI
│
├── Host integration layer
│
└── Managed Linux environment
     │
     └── NixOS
          ├── coding agent
          ├── Git/repository
          ├── compiler/toolchains
          ├── development dependencies
          ├── services
          ├── processes/logs
          ├── observability
          └── private headless desktop
               ├── Wayland compositor
               ├── virtual display
               ├── applications
               └── isolated input
```

The user should not have to:

- install/manage VirtualBox,
- manually configure a VM,
- allocate disks,
- interact with a Linux desktop,
- manually configure networking,
- manually provision the environment.

The application should manage the underlying environment.

## Why NixOS Could Be Useful

Nix/NixOS could provide a major advantage for the agent environment:

- declarative configuration,
- reproducibility,
- controlled package versions,
- rollback,
- reproducible development dependencies,
- prebuilt environments,
- environment versioning,
- easy provisioning,
- deterministic agent machines.

Potentially the entire agent machine could be defined declaratively.

Conceptually:

```nix
agentEnvironment = {
  desktop.enable = true;
  codex.enable = true;
  development.enable = true;
  observability.enable = true;
  guiTesting.enable = true;
};
```

A known NixOS image/configuration could potentially be distributed as the standardized environment.

## Private Desktop Still Applies

Inside the managed Linux environment, retain the private desktop architecture from the original project.

For example:

```text
Windows desktop
      │
      │ completely independent
      │
      ▼
Managed NixOS
      │
      └── Agent Wayland compositor
           ├── virtual 1920x1080 output
           ├── Firefox
           ├── Electron application
           ├── application under development
           └── virtual keyboard/mouse
```

The agent can:

- launch applications,
- screenshot them,
- inspect semantic UI state,
- click/type,
- reproduce bugs,
- rebuild,
- restart,
- verify fixes,

without anything appearing on the user's Windows desktop.

The Windows frontend could optionally expose:

```text
[View Agent Desktop]
```

which displays/streams the agent's virtual framebuffer.

Closing the viewer must not stop or affect the agent desktop.

## WSL2 vs Managed VM

There are at least two potential Windows implementations worth researching later.

### Option A — WSL2

Advantages:

- already integrated into modern Windows,
- good Windows/Linux interoperability,
- filesystem integration,
- networking integration,
- GUI infrastructure through WSLg,
- relatively low user friction.

Potential approach:

```text
Windows app
    ↓
WSL2
    ↓
Nix/NixOS-like agent environment
    ↓
private headless Wayland compositor
```

Important research question:

> Can our chosen Linux private-desktop architecture operate cleanly and reliably inside WSL2 without depending on the normal visible WSLg application path?

### Option B — Managed NixOS VM

Instead of depending heavily on WSL behavior, ship/manage a dedicated lightweight NixOS virtual machine.

Advantages could include:

- full control of kernel/userspace,
- known environment,
- stronger isolation,
- reproducibility,
- consistent behavior across machines,
- easier environment versioning,
- complete control over the virtual graphical stack.

Conceptually:

```text
AgentRuntime.exe
      ↓
VM lifecycle manager
      ↓
small managed NixOS VM
      ↓
agent runtime
```

The virtualization should be invisible to normal users.

This is similar conceptually to how products such as Docker Desktop hide substantial virtualization behind a normal application experience.

Do not assume either WSL2 or a custom VM is superior yet. Research and prototype later.

## Repository Access

The managed Linux environment must have efficient access to the project being developed.

Possible approaches include:

- host filesystem sharing,
- repositories stored inside the Linux environment,
- synchronized worktrees,
- Git-based synchronization.

This requires careful research because filesystem performance, Linux filesystem semantics, permissions, file watching and build workloads could make naive host-mounted repositories undesirable.

Do not assume `/mnt/c/...`-style development is necessarily the optimal architecture.

## Host Bridge

Eventually there could be a controlled bridge between the agent Linux environment and the host.

For example:

```text
Agent NixOS
     │
     ├── selected repository
     ├── Git credentials
     ├── network access
     ├── selected files
     │
     └── Host Bridge
              ↓
           Windows
```

This bridge should be capability-based rather than automatically giving unrestricted access to the host.

Potential future capabilities:

- open host file,
- notify user,
- request permission,
- access selected directory,
- open browser,
- interact with native host application.

Security boundaries should be explicit.

## Native Windows Applications

The Linux environment does NOT automatically solve development/testing of native Windows GUI applications.

Initially, this is acceptable.

The portable Linux environment would be particularly suitable for:

- Linux applications,
- web applications,
- servers,
- CLI tools,
- libraries,
- cross-platform applications,
- Electron applications,
- development tooling.

Longer term, a Windows host backend/bridge could allow the agent to test native Windows applications.

Potential architecture:

```text
                    Agent Runtime
                         │
              ┌──────────┴──────────┐
              │                     │
        Linux environment       Host bridge
              │                     │
        Linux application       Windows application
        development/testing     testing/control
```

Do not implement this initially.

## Portable Agent Machine

The larger conceptual direction is:

> The coding agent gets its own standardized computer.

Rather than depending heavily on whatever random packages/configuration exist on the host, every agent could operate inside a reproducible machine containing:

```text
Agent Machine
├── source/worktree
├── shell
├── compiler/toolchains
├── dependencies
├── processes
├── services
├── networking
├── observability
├── logs
├── checkpoints
├── private graphical desktop
├── semantic UI inspection
└── testing/verification
```

The host application manages this machine.

This could improve:

- reproducibility,
- security,
- debugging,
- agent reliability,
- portability,
- onboarding,
- environment recovery,
- parallel agents.

## Per-Task Machines

Eventually environments could potentially be cheap enough to create per:

- task,
- issue,
- branch,
- PR,
- agent.

For example:

```text
Issue #381
   └── Agent Machine A

PR #421
   └── Agent Machine B

Experimental fix
   └── Agent Machine C
```

This connects to the original ideas around parallel hypotheses, reproducible debugging and automated verification.

## Snapshots

A managed environment could make snapshot/rollback especially powerful.

For example:

```text
create clean environment
        ↓
snapshot
        ↓
agent experiment
        ↓
failure
        ↓
rollback
        ↓
different experiment
```

Eventually a debugging artifact could potentially capture:

```text
Nix environment
+ source revision
+ filesystem state
+ running services
+ desktop state
+ interaction trace
+ logs
= reproducible agent experiment
```

## Distribution

Long-term, installation could look like a normal application.

### Linux

Potentially:

```text
nix run github:<project>
```

plus packages for ordinary distributions.

### Windows

Potentially:

```text
AgentRuntime.exe
```

which handles:

- virtualization/WSL,
- Linux provisioning,
- Nix environment,
- updates,
- networking,
- filesystem sharing,
- agent communication,
- desktop viewing.

The fact that Linux is running underneath should mostly be an implementation detail.

## Important Architectural Implication

While implementing the current Linux MVP:

**Do not prematurely tie the core runtime to the physical Linux host.**

Where practical, separate:

```text
Agent API
   ↓
Agent Runtime Core
   ↓
Environment Backend
   ├── native Linux
   └── future managed Linux machine
```

Likewise separate:

```text
Desktop API
   ↓
Wayland desktop implementation
```

from assumptions about the host's physical compositor.

However, DO NOT introduce elaborate abstraction layers solely for hypothetical Windows/macOS support.

Use interfaces where natural and avoid obvious coupling, but optimize the current implementation for actually working on Linux.

## Research Questions to Preserve

Later, investigate:

1. Can the headless Wayland architecture chosen for the Linux MVP run unchanged inside WSL2?
2. Can NixOS itself practically serve as the managed WSL environment, or is Nix-on-another-WSL-distribution preferable?
3. Would a managed NixOS VM provide meaningful advantages over WSL2?
4. Which Windows virtualization technology would best support an invisible managed environment?
5. How small can the base agent image become?
6. How quickly can environments boot/resume?
7. How should updates to the agent environment work?
8. How should repositories be shared with the environment without sacrificing filesystem performance?
9. How should credentials be securely exposed?
10. Can GPU acceleration be provided to the private Wayland environment?
11. How should the optional desktop viewer work?
12. How should host ↔ agent networking work?
13. How much isolation should exist between multiple agent machines?
14. Could snapshots be cheap enough for routine agent experimentation?
15. How portable could the same managed Linux architecture eventually be to macOS?

## Product Direction

There are now potentially several levels to the project:

```text
Level 1
Private Linux desktop for coding agents

        ↓

Level 2
Linux execution/debugging environment for coding agents

        ↓

Level 3
Reproducible "agent machine" containing development,
observability, GUI interaction and verification

        ↓

Level 4
Portable application where the same managed Linux/NixOS
agent machine runs natively on Linux and invisibly behind
Windows/macOS frontends
```

Level 1 remains the immediate objective.

Do not attempt to implement Levels 3–4 now.

The purpose of recording this direction is to avoid making early architectural decisions that unnecessarily prevent it.

## Long-Term Vision

A developer should eventually be able to install the product on their computer, select a repository and assign a task.

Behind the scenes, the system gives the coding agent a reproducible Linux computer that it can fully operate:

- edit code,
- install/build dependencies,
- run commands,
- launch services,
- inspect processes,
- observe system behavior,
- launch GUI applications,
- see and interact with them,
- reproduce bugs,
- modify code,
- rebuild,
- verify behavior,
- record evidence,
- create tests.

The user can continue using their own computer normally while this happens.

The implementation details—NixOS, virtualization, Wayland, screenshots, input injection, environment provisioning—should eventually disappear behind that experience.

For now, continue prioritizing the original Linux MVP. Treat this document as a **possible future product and architecture direction**, not as an instruction to expand the immediate scope.
